## What this is

CV-2 turns `log.ge_cv_syserror` rows into `insight.ge_cv_facts` (table
from migration 007, reviewed in REVIEW-CV1-SCHEMA). It follows the GE CT
pipeline (`insight/load.js`, `insight/extract.js`, `insight/rules/`,
`insight/reconcile_sql.js`), in new files under `insight/cv/`. The GE CT
run must not change: CT Phase 5 is in its monitoring window, so no CT
file is edited and nothing CT loads requires `insight/cv/`.

**The agreed mapping** (plan §6.2), per source row:
1. **RTA relay** (subsystem `RTA` and source file `XRImChainPos`):
   ignored, no fact.
2. **Every other row:** a `cv.error` fact, dim = the error code.
3. **Plus at most one of 8 named metrics,** matched on code + readable
   debug text.

**Ground rules that the code must keep:**
- **Never read GE's encoded fields** (`errortext`, `fru`,
  `majorfunction`, `minorfunction`).
- **Write only as `insight_writer`.**
- **`--apply` is refused** until migration 007, the source grant (plan
  §7.4 C2) and the CT verifier change (C1, marked by `CV_AWARE = true`
  exports) are all in place.

## Please look at

1. **Independence of the check.** Is `reconcile_sql.js` really
   independent of `rules.js`? Could both share a mistake? Compare each
   `COND` with its rule, especially:
   - the anticollision text and dim;
   - JS `.test` vs PostgreSQL `~` on the debug text (quotes, leading
     spaces, case).
2. **Correctness of `load.js`:**
   - the version-gated upsert on `ge_cv_facts_source_key` (the
     `DO UPDATE` set);
   - the batch transaction: facts, watermark and pending days commit
     together, and the stats are only taken on commit;
   - the late-commit re-read: its `NOT EXISTS` on the source key, the
     2-hour window, and the relays it re-reads every time;
   - `record_derive_pending`: creating the `ge_cv_derive` row and the
     FOR UPDATE merge.
3. **Interlocks.** Are C1 (`CV_AWARE` on the three CT verifier modules)
   and C2 (`has_table_privilege`) checked at the right time, and are they
   impossible to bypass by accident? Is refusing `--apply` but allowing
   `--rehearse` before C1 sound? The rehearsal writes `cv.*` catalog rows
   inside a transaction that is rolled back.
4. **Shared-table effects.** CV writes `insight.metric_catalog` (via
   CT's `catalog_statement`) and `insight.job_state` (`ge_cv_extract`,
   `ge_cv_derive`). Can either affect a GE CT run, apart from C1? For
   example: lock waits on `metric_catalog` during CT's catalog upsert,
   or anything CT reads from `job_state`.
5. **The rule-error policy.** A rule error, or a row matching two named
   metrics, aborts the batch, where CT counts it and goes on. Is that the
   right choice for a manual backfill? (The stage comes later, in CV-5.)
6. **Fixtures and data handling.** Fixtures keep the code, subsystem,
   debug text, source file, repeatcount and source line, with IPv4
   masked. Is anything there sensitive? Is any SQL able to select an
   encoded field?
7. **Gaps.** Anything the CV-2 exit criterion needs that is missing, or
   that CV-3 (derive) will need from the facts or the pending days?
