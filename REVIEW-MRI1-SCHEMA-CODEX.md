# Review: MRI-1 schema (migration 009)

## Findings

No blocking schema or rollback defect found in migration 009.

## Reviewed paths

- **Existing objects:** 009 creates only new `insight.ge_mri_*` relations, indexes, partitions, and a sequence. Its only references to shared schema objects are the two metric-catalog foreign keys. It does not change the definitions, grants, or rows of existing CT/CV objects. The runner already includes all `insight.*` objects in scope, so these additions are covered without changing its allowlist.
- **Key and time:** the unique key is the gesys natural key plus `metric_key`, with `host_local` required by PostgreSQL's partitioned unique-key rule. The CHECK makes `host_local` a deterministic function of integer-second `epoch`; integer-by-`interval '1 second'` is appropriate here, including negative values, and is within range for the stated dates. The natural key can collide at a repeated device-local time in a DST fold. The chosen dedupe trade-off is consistent with §5.3 Q-M9 provided MRI-2's independent verification fails the load when a key maps to different source records; the schema alone cannot retain both records under that collision. The source primary-key columns remain available for that check.
- **Partitions and daily rows:** timestamp-without-time-zone bounds correctly represent device wall-clock months and support partition pruning on `host_local`. No default partition matches the CT pattern, with out-of-range rows needing to be counted by the extract. The daily CHECK compares timestamp dates directly and is safe for device-local rollups. The 2028-12 horizon is an operational maintenance point, not a schema defect; the writer cannot extend it.
- **Codes and rollback:** nullable `category` represents unreviewed codes, and the constraint limits non-NULL values to the six reviewed groups. The schema stores no raw message text. The down file revokes the grants and drops the three parent tables without CASCADE; their partitions and owned sequence are dependent objects and are removed with the facts table. Shared catalog/job/finding rows are deliberately retained, as documented.
- **Shared-table consumers (C1-MRI):** the three CT verification paths identified in §6.4 are the direct correctness gates: [verify_facts.js](/home/matt-teixeira/hep3/hhm_rpp_ge/insight/verify_facts.js:14) and [derive/verify.js](/home/matt-teixeira/hep3/hhm_rpp_ge/insight/derive/verify.js:278) count every metric except `cv.*`; [findings/verify.js](/home/matt-teixeira/hep3/hhm_rpp_ge/insight/findings/verify.js:20) accepts every finding key except `cv_*`. Once MRI registry rows are written, those CT catalog checks will count MRI rows as CT and fail. This does not affect applying 009 because it writes no shared rows, but the CT-prefix scoping change and MRI apply interlock must precede the first MRI catalog upsert.
- **Other shared-table interactions:** CT's `derive/verify.js` capability comparison reads all of `insight.system_capabilities`; keeping MRI out of that table is necessary and sufficient for that path. The CT API views that read capabilities likewise remain safe under this design. The current CT findings API view is source-filtered by migration 008. I found no other CT/CV correctness gate that treats MRI rows in `metric_catalog`, `finding_catalog`, `findings`, or `job_state` as its own rows.
- **CV stage rehearsal:** [cv/stage.js](/home/matt-teixeira/hep3/hhm_rpp_ge/insight/cv/stage.js:142) fingerprints all rows except `cv.*`/`cv_*`, so future MRI shared rows are included in its “non-CV” baseline. They are read from a repeatable-read snapshot and are not modified by the CV rehearsal; therefore this alone does not cause a failure. An MRI write concurrent with the rehearsal is a coordination concern for the shared-stage wrapper, as noted in the plan, rather than a schema-009 defect.
- **Source-log permission:** `insight_writer` still needs the separately coordinated SELECT grant on `log.ge_mri_gesys` before MRI-2 can run. 009 correctly leaves that protected source relation unchanged.

## Verification

This was a source review only. I did not run tests, migration commands, or database connections; the handoff reports those checks and the local PostgreSQL roundtrip.
