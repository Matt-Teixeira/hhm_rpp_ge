## What MRI-2 is for

It turns `log.ge_mri_gesys` into `insight.ge_mri_facts` under the agreed
mapping (plan §5): every deduped record gives `mri.error` (dim = message
code), plus the 22 named metrics its code lists (at most two; the exam
summary 2218650 gives `mri.scans_ok` and `mri.scans_failed`). Records
dedupe on the gesys natural key `(system_id, epoch,
record_number_concurrent)`; `host_local` = 1970-01-01 + `epoch` (009's
CHECK).

**Agreed with the user:** the mapping (Q-M1–Q-M10); the natural key
(Q-M9); catalog rows from the registry, not the migration; **no change to
any CT or CV file, the root `index.js`, or shared `insight/` files**
(the freeze until 2026-11-19); nothing written to prod.

## Please look at

1. **Mapping fidelity.** Does `rules.js` implement plan §5.2 /
   `PLAN-MRI-INSIGHTS-CODES.md` §1 exactly (codes, dims, value regexes,
   the dsserver exclusion, 200002379 not counted)? Is any matcher looser
   or tighter than the definition? Is the independent SQL
   (`reconcile_sql.js` COND) truly independent and equivalent (JS regex vs
   PostgreSQL `~` / `LIKE`, `^` anchoring, multi-line messages,
   `\S`)?
2. **Dedupe and conflicts.**
   - First-row-wins: is it stable across batches, late commits (a lower id
     arriving after a higher one), and a re-extract after a version bump?
   - Is md5(code, type, message) the right "same record" test? Should
     `coil` / `psd` / `host_datetime` be in it?
   - `EXISTING_SQL` joins stored `mri.error` facts back to the source by
     `(id, capture_datetime)`. Any case where a conflict is missed (e.g.
     a key whose first row was unstorable, or two copies in one batch plus
     a stored third)?
   - The rehearsal's second pass skips the conflict check: acceptable?
3. **Write-path safety.** Per-batch atomicity (facts, watermark, pending
   days); the upsert never changing the key or the source columns; the
   late re-read; the advisory lock; preflight order (schema USAGE before
   `has_table_privilege`); `--from-id` gap guard. Anything that could
   write a partial batch or skip rows?
4. **Shared tables.** The catalog upsert (`insight/load.js`
   `catalog_statement`) writes 23 `mri.*` rows to `metric_catalog`; job
   rows `ge_mri_extract` / `ge_mri_derive`. With C1-MRI pending, is the
   `MRI_AWARE` interlock enough, given the rehearsal writes catalog rows
   (rolled back) without it?
5. **Privacy.** No fact stores message text; dims come from fixed lists,
   process names and the software version; `mri.error` attrs are process,
   coil and psd. Fixtures: is the masking enough (hosts, system ids, MAC,
   IP, serial, UDI, AE titles)? Anything identifying left in
   `__fixtures__/`?
6. **Isolation.** The tests check that nothing outside `insight/mri`
   (CT, CV, root `index.js`) requires it, and that it requires nothing in
   `insight/cv`. It does require shared CT modules (`../db`, `../load`,
   `../rules/engine`), read-only. Any load-time side effect of those that
   matters?
7. **Verify as the exit gate.** Are the checks in `verify.js` sufficient
   for "extract equals independent SQL per system × metric", and is
   anything it should fail on missing?
